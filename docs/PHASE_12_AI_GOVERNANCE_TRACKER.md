## Product boundary

GuardAI records three separate concepts:

1. organization declaration,
2. documentation state,
3. legal applicability state.

The third state is always:

```text
requires_human_review
```

A documented control is not represented as legal compliance. GuardAI does not automatically classify an AI system as prohibited, high-risk or otherwise regulated.

## Versioned official source registry

`shared/legal-sources/eu-ai-act-guided-review-v1.json`

Registry:

```text
eu-ai-act-guided-review@1
```

Current official EUR-Lex anchors:

- Regulation (EU) 2024/1689, Article 4 — AI literacy,
- Article 14 — Human oversight,
- Article 50 — Transparency obligations for providers and deployers of certain AI systems.

These are review anchors only. Applicability is not inferred from the existence of a declaration or technical signal.

## Structured declaration model

`server/domain/aiGovernanceEvidence.js`

Allowlisted fields:

- system name,
- organization role (`provider`, `deployer`, `both`, `unknown`),
- optional provider/model names,
- deployment context,
- bounded use-case enum,
- six `yes/no/unknown` declarations.

The HTTP schema is strict. Unknown top-level or nested fields are rejected.

Explicitly outside this MVP schema:

- raw prompts,
- model outputs,
- customer content,
- arbitrary personal data,
- free-form legal conclusions,
- automatic AI Act risk-class assignment.

## Persistence

Design drafts only — not applied migrations:

- `database/026_ai_governance_guided_review_draft.sql`
- `database/027_ai_governance_review_cycle_invariant_draft.sql`

Source model:

- `ai_system_profiles`
- `ai_governance_reviews`
- `ai_governance_review_items`

Key invariants:

- tenant-scoped composite relationships,
- Browser roles are read-only; mutations go through backend authorization,
- AI System profile uses typed columns rather than arbitrary declaration JSON,
- review snapshot is generated by a DB trigger from the typed profile,
- review snapshot/system/source-registry provenance cannot be rewritten,
- AI System deletion cannot cascade-delete historical reviews,
- system is archived instead of deleted by the product workflow,
- exactly one open review cycle per AI System,
- historical `reviewed` cycles remain available,
- legal applicability column is constrained to `requires_human_review`,
- review status changes produce Audit Events.

## RBAC

- Viewer: read systems/reviews.
- Member: create/update systems, create draft review, submit/re-submit review.
- Admin/Owner: all above + archive system, mark review reviewed, reopen review.

`reviewed` means a human reviewer completed the GuardAI review workflow. It does **not** mean legally compliant.

## API source

Mounted under `/api/v1`:

- `GET /organizations/:organizationId/ai-systems`
- `POST /organizations/:organizationId/ai-systems`
- `GET /organizations/:organizationId/ai-systems/:systemId`
- `PUT /organizations/:organizationId/ai-systems/:systemId`
- `POST /organizations/:organizationId/ai-systems/:systemId/archive`
- `POST /organizations/:organizationId/ai-systems/:systemId/reviews`
- `GET /organizations/:organizationId/ai-governance/reviews`
- `GET /organizations/:organizationId/ai-governance/reviews/:reviewId`
- `POST .../:reviewId/submit`
- `POST .../:reviewId/review`
- `POST .../:reviewId/reopen`

Client cannot submit legal-source IDs, applicability decisions, review source-registry versions or arbitrary review items.
